# D1 server/API

The server needs Node 24.21.0, a private PostgreSQL database, and an external private-access boundary. No public login is provided. `APP_ORIGIN` is the exact browser origin, including a non-default port; the proxy must preserve its Host header. Direct non-browser clients may omit Origin but must still use that Host. JSON mutations reject cross-site browser requests. No wildcard CORS is enabled.

Build and provision explicitly (runtime never runs migrations):

```sh
mise exec node@24.21.0 -- npm run build
# Set DATABASE_URL and APP_ORIGIN in the environment, not the command history.
mise exec node@24.21.0 -- npm run db:migrate
mise exec node@24.21.0 -- npm start
```

`HOST` defaults to `127.0.0.1`, `PORT` to `3000`. `TRUSTED_PROXIES`, if set, is a comma-separated list of IP addresses or CIDRs. Supply only trusted reverse proxies. No forwarded header is trusted by default. HTTPS and network access control belong to the deployment. Readiness checks database connectivity and required schema objects; it does not test an external provider. OpenAPI is at `/api/v1/openapi.json`; `/api/v1/events` emits advisory invalidations, not a replayable log. Reconnect clients must reload snapshots.

FreshRSS is opt-in: set `FRESHRSS_ENABLED=true`, `FRESHRSS_BASE_URL` (ending in `/api/greader.php`), `FRESHRSS_EMAIL`, and either `FRESHRSS_API_PASSWORD` or `FRESHRSS_API_PASSWORD_FILE` (absolute file path). Otherwise the reader works without credentials and import start returns 503. Import writes article metadata and acknowledgement intents only; D1 does not create per-article processing tasks. Production FreshRSS read acknowledgements are hard-disabled in the client, including when configured. Pending acknowledgements remain visible in run counts. Do not remove this gate until isolated V5 and digest-compatibility evidence exists; fixture tests are not that evidence. No real FreshRSS service is used by normal tests.

## External mail queue

This application does not send email. An external consumer reads `GET /api/v1/mail-queue?limit=50&cursor=...` (limit 1–100, default 50), sends mail, then posts `{ "articleIds": ["UUID", ...] }` to `/api/v1/mail-queue/acknowledgements` (1–100 IDs; duplicates are collapsed). Responses separate `confirmed`, `alreadyConfirmed`, and `rejected` entries (`NOT_FOUND` or `NOT_SELECTED`). Acknowledgement marks selected articles sent; retries are idempotent. A sent article cannot be selected or reset: `PUT /api/v1/articles/:id/mail-selection` with `{ "selected": true|false }` returns `409 MAIL_ALREADY_SENT`. Selection is independent of read state and FreshRSS acknowledgements. All writes require the existing same-origin/JSON protections and an online connection.

Queue items are selected-unsent, ordered by selection timestamp and UUID ascending. `nextCursor` is opaque; pagination is neither a snapshot nor a lease. Consumers must coordinate sends and retries themselves. In particular, a successful external send followed by a lost acknowledgement can result in duplicate email: this API cannot guarantee exactly-once delivery.

Items include original metadata and the stored article content where available. `content.status` is `missing`, `limited`, or `available`; quality, limitation, failure code and capture metadata are exposed without waiting for processing. Transcript has `missing` status and null text. A summary has `missing` status and null text when none is saved; otherwise it has `available` or `limited` status and the saved text. A summary is `limited` if it has an explicit limitation or its content revision is outdated. No content is invented or fetched by queue reads.

## Saved summaries (read-only slice)

`GET /api/v1/articles/:id/summary` returns 404 for an unknown article, or `{ "status": "missing" }` when no summary is saved. A saved summary returns `status`, `text`, `contentRevision`, `limitation` and ISO `completedAt`. Status is `outdated` if the saved content revision differs from the article revision, otherwise `limited` if a limitation exists, otherwise `current`. An outdated result can also have a limitation. This read creates no work; the online-only reader displays saved text and provenance. No generation or regeneration endpoint is added by this slice. D5/V20 remain incomplete.

## Targeted feedback

`GET /api/v1/articles/:id/feedback` lists the article's current tags and source plus previously voted detached tags, with each target's vote and timestamp. `POST /api/v1/articles/:id/feedback` accepts `{ "value": -1|0|1, "targets": [{ "type": "tag"|"source", "id": "UUID" }] }`. Targets must be distinct and nonempty; an invalid target rejects the whole request. A tag must be currently attached or have a retained vote; a source must be the article's current source. Each explicit action refreshes its vote timestamp, including repeated values and zero. `DELETE /api/v1/articles/:id/feedback/tags/:tagId` and `/sources/:sourceId` remove votes idempotently; send a JSON body such as `{}` under the mutation policy. Detached votes remain editable until removed. Feedback does not modify scores or enqueue tasks. Score-context integration remains unimplemented.

## Preference administration

`GET /api/v1/settings/source-permissions` returns `{ "sources": [{ "id", "contextId", "externalFeedId", "title", "override" }], "hostRules": [{ "host", "allowed" }] }`. Overrides are boolean or null (inherit). `PATCH /api/v1/sources/:id/fallback-permission` accepts exactly `{ "override": boolean|null }` and returns `{ "ok": true }`; an unknown source returns 404. `PUT /api/v1/settings/source-permissions/host` accepts exactly `{ "host": string, "allowed": boolean }` and returns the canonical exact-host rule. Invalid hosts return 400; rules are not suffix or wildcard matches. Permission does not validate or initiate network access and is not yet wired into preparation.

`GET /api/v1/settings/preferences` returns `{ "halfLifeDays": 90 }` by default. `PATCH` to the same path accepts exactly `{ "halfLifeDays": number }`, finite and positive. `PATCH /api/v1/tags/:id/preference` and `/api/v1/sources/:id/preference` accept exactly `{ "manualOffset": number }`, finite, and return `{ "id", "manualOffset" }`; missing IDs return 404. Settings and offsets persist independently of import settings. Mutations increment the catalog revision and do not enqueue work or recompute scores.

`GET /api/v1/preferences/tags` and `/api/v1/preferences/sources` return `{ "asOf", "halfLifeDays", "items", "nextCursor" }`. Items contain `id`, `label`, `manualOffset`, unrounded `weight`, and raw `positive` and `negative` counts. Detached tag votes are included; neutral votes affect neither count. `query` is a case-insensitive literal substring of the label (maximum 200 characters). `sort` is `name` (default), `weight`, `positive`, or `negative`; `direction` is `asc` (default) or `desc`, with UUID ascending as tie-breaker. `limit` is 1–100 (default 50). Cursors are opaque and bound to query, sort, direction and type; retain those parameters for subsequent pages. Their calculation time and half-life are fixed across pages. Pagination is not a data snapshot: concurrent changes may shift results, and a stale cursor can return 400; restart the listing. Weights decay votes at the reported time but never decay offsets.

## Tag merge

`POST /api/v1/tags/merge` accepts `{ "targetId": "UUID", "sourceIds": ["UUID", ...] }`. The list has 1–100 distinct sources and excludes the target; all tags must exist and be active. Invalid input returns 400, missing tags 404, and archived tags 409. Success returns `{ "ok": true }`. The transaction sums offsets, unions associations, combines all votes per article by the sign of their original sum and retains the latest vote timestamp, including detached votes. It deletes source tags and increments affected assignment revisions and the catalog epoch. It does not recompute scores or enqueue tasks. The online Preferences interface provides half-life and offset editing, preference browsing, and tag selection and merge. The catalog epoch and assignment revisions are stored for fencing, but future asynchronous classification and scoring publishers are not yet wired to enforce these fences; this slice does not establish safety for those future workers. Local functionality is not deployment or user acceptance: the private access boundary and deployment verification remain necessary.

## Catalog administration (local slice)

`GET /api/v1/categories` and `/api/v1/tags` return `{ "items": [...] }`, including archived records. `POST` to either collection accepts `{ "label": "..." }`; `PATCH /api/v1/categories/:id` or `/api/v1/tags/:id` accepts exactly one of `{ "label": "..." }` or `{ "archived": true }`. Responses are the created or updated record (201 or 200); an unknown ID returns 404. Labels must be nonblank and at most 200 Unicode code points after trimming or tag normalization. Category collisions compare trimmed labels case-insensitively; tag labels use NFKC/whitespace normalization and PostgreSQL Unicode casefold identity. Archived names remain reserved. Collisions return 409; invalid input and attempts to archive the fallback category return 400. Archiving is idempotent, retains existing assignments, and archived tags cannot be newly attached. The fallback category can be renamed but not archived. These routes use the same JSON/origin security policy as other mutations.

## Score-definition administration

`GET /api/v1/scores` returns `{ "items": [...] }`, including deleted definitions. `POST /api/v1/scores` requires exactly `name`, `description`, `prompt`, `active`, `includeTitle`, `includeContent`, `includeCategory`, `includeTagWeights`, and `includeSourceWeight`. `PATCH /api/v1/scores/:id` accepts a nonempty subset of those fields. Text must be nonblank, contain no NUL, and be at most 200, 2,000, and 10,000 UTF-16 code units respectively; flags must be JSON booleans. Unknown fields are rejected. The shared HTTP body limit is 16 KiB, including JSON encoding. Existing records may have empty descriptions from older writes. Responses return the definition including `id` and `deletedAt`; creation returns 201. Invalid input returns 400, unknown IDs 404, and editing a deleted definition 409 `DELETED`.

`DELETE /api/v1/scores/:id` requires JSON (e.g. `{}`), sets `active` false and persists `deletedAt`; repeating it returns the original deletion timestamp. Historical article scores are retained. Deleted definitions cannot be edited or reactivated. The 0–100 range applies to results, not definitions.

`GET /api/v1/scores/:id/category-prompts` returns `{ "items": [{ "scoreId": "UUID", "categoryId": "UUID", "prompt": "..." }] }`, including stored overrides for subsequently archived categories. `PUT /api/v1/scores/:id/category-prompts/:categoryId` accepts exactly `{ "prompt": "..." }` and returns the override. Prompt text must be nonblank, NUL-free and at most 10,000 UTF-16 code units. `DELETE` on the same path requires exactly `{}` and returns `{ "removed": true }`, including when the override did not exist. Both IDs must be valid UUIDs. Unknown scores/categories return 404, deleted scores 409, and archived or fallback categories 400 on mutations; fallback always uses the global prompt. Invalid requests leave stored overrides unchanged. Disabled but nondeleted scores are allowed.

These routes use the existing origin/Host/JSON policy and require a private access boundary. Score execution is available only through the explicit, dormant task workflow below; definition edits do not enqueue work or recalculate scores.

## Saved score results (read-only)

`GET /api/v1/articles/:id/scores` returns 404 for an unknown article and otherwise `{ "items": [...] }`, one item per score definition, including inactive and soft-deleted definitions. Items contain `scoreTargetId`, `name`, `active`, `deleted`, `value`, `calculatedAt`, `contentRevision`, `assignmentRevision`, `stale`, `condensed`, `limited`, and `latestTask`. Result fields are null when no successful score is stored. `stale` compares both saved revisions to the article's current revisions. `latestTask` is null or `{ "generation", "state", "errorCode" }`; latest means highest generation, then creation time and ID. A newer failed task does not replace the saved score. One database statement reads a consistent snapshot and does not expose prompts or configuration. The online-only reader shows these results separately from reevaluation; this read creates no work.

## Category and tag task diagnostics

`GET /api/v1/processing-tasks/:id` also returns category and tags tasks, discriminated by `action`. Their fields are `id`, `articleId`, `action`, `scoreTargetId` (always null), `generation`, `state`, `errorCode`, `createdAt`, `updatedAt` and `endedAt`. Unknown IDs and unsupported actions return 404. Internal task metadata, receipts, hashes and request configuration are not returned. Score and Karakeep responses retain their existing shapes. Advisory `task.changed` events include category, tags and scores in the latest 100-task polling window; events can be missed and clients must reload authoritative GET state.

## Direct score reevaluation (dormant)

`POST /api/v1/articles/:id/reevaluations` accepts exactly `{}` and returns `202 { "tasks": [{ "taskId", "scoreTargetId", "generation", "state" }] }` for each active, nondeleted score definition; no active definitions yields an empty list. Unknown articles return 404. Each explicit request creates fresh generations, supersedes older unfinished score tasks, and transactionally admits retry-disabled pg-boss jobs. `GET /api/v1/processing-tasks/:id` returns the score task's article/target/generation, state, error code, and timestamps; Karakeep tasks retain their existing status shape; category and tags tasks use the diagnostics shape above. Unsupported actions return 404.

Normal composition registers the worker but resolves no score model capabilities and injects a fail-closed AI stub. Without separately implemented and authorized model wiring, tasks settle visibly as `needs_input/configuration_required`; no provider call or production inference is activated. Queue provisioning occurs only through explicit `npm run db:migrate`, not server startup. Article detail exposes an online-only explicit reevaluation action. It displays admission identities but uses GET for authoritative task state and error code, refreshes on SSE invalidation and reconnect, and polls nonterminal or unconfirmed tasks at three-second intervals for at most 20 attempts per refresh. A failed status read displays the last confirmed state as such. A lost or ambiguous POST response may have created tasks whose IDs are unknown; a new action creates fresh generations rather than retrying the old request. Task display is cleared on leaving or changing article and is not persisted. This direct-only workflow has no import admission/backfill, category/tag chain or startup score-task recovery; it is not D2/C14 acceptance.

## Manual article catalog assignment

`GET /api/v1/articles/:id/catalog` returns `{ "category": { ... }, "tags": [ ... ], "assignmentRevision": 0 }`, including archived current assignments. `PATCH /api/v1/articles/:id/category` accepts exactly `{ "categoryId": "UUID" }`. `PUT` and `DELETE /api/v1/articles/:id/tags/:tagId` attach or detach a tag; send JSON, for example `{}`, under the mutation policy. Successful writes return `{ "ok": true }`. Invalid UUIDs or bodies return 400; unknown article or catalog IDs return 404; assigning an archived category or attaching an archived tag returns 409 `ARCHIVED`. Only active categories and tags are assignable; the protected fallback is an active category. Archived tags remain visible and detachable. Repeated writes are idempotent: each actual category or association change increments `assignmentRevision` once; no-op writes do not. Writes serialize against other assignment writes and catalog archive, and do not remove retained tag votes, change read/mail/score state, enqueue tasks or trigger reevaluation. The reader editor requires an online connection; changes are not queued offline.

## Reader

List filtering and date/title/score sorting happen before pagination. Date descending remains the default. For `sort=score`, provide an explicit active, non-deleted `scoreId` UUID; missing, unknown, inactive, or deleted IDs return 400. `scoreId` is not accepted for other sorts. Values sort in the selected direction with nulls last, then coalesced publication/import date descending and UUID descending. Each list item has `scoreValue`, null when no value exists or no score is selected; detail and mutation responses return null. No scores are calculated by reader requests. Cursor contents are opaque to clients and bind the filter/sort query. They are not snapshots: reload from page one after mutations. Manual category/tag assignment and explicit dormant score reevaluation are available; normal composition does not enable score inference or article enrichment, and the reader returns preparation as unavailable rather than fabricating a result. The build includes the same-origin reader UI at `/`. The API exposes source IDs, not a source catalog; the reader's source filter accepts a source UUID. The service worker precaches only the versioned shell and build assets; API and event requests remain network-only. Offline changes are not queued. The reevaluation UI tracks tasks admitted during the current article view; the score results UI separately shows each target's latest task, not a full task history or manual retry.
