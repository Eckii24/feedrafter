# Karakeep preparatory client

The local server action and explicit reader UI are wired to this adapter. The integration is disabled by default. `KARAKEEP_ENABLED=true` requires `KARAKEEP_BASE_URL` as an HTTP(S) base **authority** (no path, credentials, query or fragment) and exactly one of `KARAKEEP_TOKEN` or `KARAKEEP_TOKEN_FILE` (absolute path). Compose passes the file setting; place it on the existing private `/data` mount. Provision queues with the explicit `migrate` command before starting workers. Never enable a deployed service until the response gate below is satisfied.

The reader discovers configuration via GET `/api/v1/karakeep` (`available`); this is not a remote health check. With a suitable original URL, its online-only save action submits once, polls the returned task and displays only confirmed results. A 503 hides the action until reconnect; failures retain the last known status. Task tracking is in memory: after a page reload, explicitly saving again reuses the existing server task. The client sends requests only to fixed paths on that authority, rejects redirects and bounds time and response bytes. Article URLs are payload/query data, never request destinations. No ambiguous dispatch is retried. POST `/api/v1/articles/:id/karakeep` with `{}` returns a task ID; GET `/api/v1/processing-tasks/:id` shows its state. Repeated requests reuse the same task even after success or uncertainty. On `needs_input`, inspect Karakeep manually; do not infer absence or repeat the create. A running intent left without a live job is fenced and marked uncertain, including when a crash happened before the actual request.

A definitive 401/403 pauses this worker process: that task and subsequent undispatched tasks become `paused_auth`, with no further Karakeep requests from the worker. Repair deployment credentials and restart the worker; startup atomically requeues paused tasks once. If credentials are still invalid the worker pauses again; periodic recovery never resumes paused tasks. A crash before the auth outcome is persisted leaves a running intent uncertain, not eligible for automatic resumption. Only one Karakeep worker process should be active for this integration: the latch is process-local, not a cross-process coordination mechanism. The reader displays the pause and continues polling for recovery.

## Provisional representations

C23 specifies 200 existing / 201 created and ID, link type and URL semantics, but does not specify a versioned JSON schema. For preparation only, create accepts a JSON object with nonempty string `id` and `content: { type: "link", url: "<exact original URL>" }`; extra properties are ignored. 401/403 produces `auth_error` without depending on the response body. Any other status, body, URL (including a normalized variant), transport failure, cancellation or timeout is `uncertain`. This candidate shape is not evidence of upstream or deployed compatibility.

C23 specifies the check-url path but no documented response fields, status mapping, absence or normalization semantics. The repository-owned lookup result representation is therefore `{ kind: "auth_error" }` for 401/403, and `{ kind: "uncertain" }` for every other response, including 200, 404 and empty objects. No response can establish presence or absence yet. Never use this result as permission to retry a create. No raw response is exposed.

Before live use, independently establish the deployed API version, response shapes, duplicate behavior and fragment/trailing-slash normalization using an authorized isolated fixture; encode and test supported lookup outcomes. The local server action does not retry uncertain requests, including manually. V22 remains a separate deployed compatibility and acceptance gate. No live service was contacted by this slice.
